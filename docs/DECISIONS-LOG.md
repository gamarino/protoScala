# Decisions log

Decisions taken during implementation, with who took them. Entries were marked
**[agent, pending review]** when taken by the implementing agent under the
maintainer's authorisation of 2026-09-22 ("decide what is missing and correct
it tomorrow").

**Review of 2026-09-23.** The maintainer has now ruled on every one of them.
The original wording of each decision is kept as it was written; the ruling is
recorded beside it. Four outcomes are not a plain approval:

- **D47 overturned** — `Future.apply` now takes its body **by name**,
  `Future(expr)`. Ruling: *least surprise for the Scala programmer*. By-name
  parameters were implemented as a general language feature to make it possible,
  with the new deviation **D53** for the call sites the compiler cannot resolve.
- **D45 overturned** — an actor handler may return a bare `newState` as well as
  `(newState, reply)`; with no reply the ask's future completes with `()`. Same
  ruling: forcing a handler that only updates state to invent a reply is the
  surprise to remove.
- **D44 superseded** — rather than leaving Phases 3 and 4 unbuilt, the maintainer
  directed that both be completed. The version implication of D44 (Phase 5
  shipping as 0.3.0 ahead of them) is to be revisited when they land.
- **D46 stands as approved**, with its stated precondition now met: it deferred
  unanchoring "until `ProtoMap` lands", and `ProtoMap` shipped in protoCore
  2.0.0 and is merged and released. It is ready to revisit; the behaviour is
  unchanged for now.

Two entries are **acknowledged, not approved as done**: ThreadSanitizer was
never run against the actors, and the cold-start budget is not claimed as met.
They stay visible as known gaps.

Two items remain **open for the maintainer** — see "Still open" at the end of
this file.

## The four escalations

| # | Decision taken | Argument | Proved how | Cost to reverse |
|---|---|---|---|---|
| **E1** | **Where the in-flight exception value lives while the stack unwinds: option (c).** Every frame the exception passes through re-roots it in its own `ProtoContext::returnValue`, unconditionally and before the handler search | protoCore's root scan reads `currentCtx->returnValue` for every context on the thread's context stack (`protoCore/core/ProtoSpace.cpp:352-356`), and `~ProtoContext` anchors a non-null `returnValue` into the **parent's** young chain before submitting its own young generation (`ProtoContext.cpp:239-258`). Writing the payload there therefore makes it a root in every frame it passes through, rather than leaving it to protoCore's generational timing | **Not proved by breaking the premise, and this entry says so rather than claiming otherwise.** `20-exceptions/catch-payload-survives-unwinding.scala` and `catch-payload-survives-a-concurrent-collector.scala` exercise the path (400 and 200 throws through 60- and 40-frame chains, under collector pressure, with a second thread allocating) and are green — but deleting the re-rooting line leaves them green too. Two things mask it: the handler entry writes the payload into a traced automatic local *before* anything on the handler path allocates, and a freshly submitted young generation is not a candidate of the same collection cycle. The window is not observable from the language, and an attempt to force a collection inside it by calling `triggerGC()` from the C++ catch crashed with and without the re-rooting, so it proved nothing. The line is kept as the guarantee that the payload's reachability does not depend on either masking effect | Removing it is one line and, today, unobservable. Adding a per-thread pin stack instead is additive and costs one attribute write per throw |
| **E2** | **The handler search sits OUTSIDE the C++ catch block**, as a retry loop around `runLoop` (`ExecutionEngine::runFrame`): the handler body is entered by `continue`, so it runs with no live C++ handler | The plan's stated reason — that entering the handler inside the catch breaks cooperative `await` — **did not hold when tested**, and this entry corrects it: a `FutureYield` thrown from a handler body entered inside the catch propagates out perfectly well, the snapshot's `ip` points into the handler body, and the resume re-enters it through `runFrame` with nothing in flight. The real reason the retry loop is required is stronger and simpler: **a frame must be able to catch a second exception** — one raised by its own handler body, by a non-matching cascade's `RETHROW`, or by a `finally` — and only a loop that re-enters the frame's own `try` region can. Entering the handler from inside the catch abandons the retry loop, so the frame's handler table is no longer consulted | **Proved by breaking the premise.** Replacing the `continue` with a recursive `runLoop` call from inside the catch turned **11 fixtures red**, including `nested-try`, `nested-try-braces`, `catch-in-a-loop`, `catch-in-a-loop-braces`, `finally-in-a-loop`, `finally-runs-on-failure`, `finally-that-throws-replaces` and `rethrow-from-a-handler` — each of them an exception the frame could no longer catch. It also grows the native stack once per caught exception, which `finally-in-a-loop`'s 100000 cycles would overflow | Doing it inside is a smaller diff and a loud, immediate defect rather than a silent one — the 11 fixtures are the guard |
| **E3** | **A0-7's six invariants are adopted as written**, with `resumeFrames` calling `runFrame`, no `finally` on a suspension, and a failed `await` raising at its call site (retiring **D50**) | Each invariant is one code path, and each now has a fixture whose failure is visible | **Proved by breaking the premise, invariant by invariant.** Invariant 1: `ScalaThrowShape.AFutureYieldIsNotAStdException`. Invariant 2 — making `runFrame` run the Finally handler on a `FutureYield` turned `finally-does-not-run-on-suspension.scala` red (`cleanup cleanup body=1` instead of `cleanup body=1`) and `await-inside-finally.scala` red (an uncaught sentinel). That fixture was **rewritten** when the first version proved toothless: it counted cleanups in a local variable, and the frame snapshot is taken before the retry loop sees the suspension, so a wrongly-run cleanup's increment was discarded and the fixture passed with the bug present. It now prints from the cleanup instead. Invariant 3 — pointing `resumeFrames` back at `runLoop` turned `await-inside-finally.scala` red (the resumed frame had no handler table, so the `RETHROW` after the cleanup escaped and the outer `catch` never saw it). Invariant 4 is covered by `await-inside-catch.scala`, which reads `e.getMessage` after a suspension inside the handler; the saving mechanism is Phase 5's and was not broken on purpose. Invariant 5 — restoring the old abandon-the-chain behaviour turned `await-a-failed-future-inside-try.scala` and `await-a-failed-future-runs-the-finally.scala` red. Invariant 6 — removing `deliver`'s `catch (ScalaThrow&)` made `actor-survives-a-handler-exception.scala` produce no output and `await-a-failed-future-inside-try.scala` time out | Each invariant is one code path; the named fixtures are what would catch a regression |
| **E4** | **Extension methods are global and session-wide (D82), with no import scoping**, and an extension whose name collides with an existing member of the receiver type is a **compile error** (D83) | This is a public-surface and scheduling question, not a protocol one. Scoping an extension needs an import mechanism, and protoScala has none: `import` is parsed and ignored, and the mechanism arrives with UMD in Phase 6 (ROADMAP). Shipping unscoped extensions now is what makes the feature usable at all, and it is what closes Phase 3's custom-interpolator restriction. The collision error is what keeps the unscoped form from being unrecoverable: silently shadowing `String.length` for a whole session would be a defect nothing could undo | Argument plus the compile-time collision check; no protocol is involved, so no breaking test is owed | Adding import scoping later is additive for code that does not rely on the global visibility, and Phase 6's done-when now records it |
